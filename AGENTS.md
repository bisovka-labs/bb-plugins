# Bisovka bb plugins — agent rules

This repository is the single home of every bb plugin and bb improvement
Eugene builds. It is also a bb marketplace (`marketplace.json`, name
`bisovka`), so sharing all of it is one command:
`bb marketplace add git:https://github.com/bisovka-labs/bb-plugins.git@main`.

## Layout

- `<plugin-id>/` — one plugin per top-level directory, named by its plugin id.
  The id is the package name minus `bb-plugin-` (`bb-plugin-todo` → `todo`).
- `app-patches/` — patches to the bb.app bundle that a plugin cannot do.
  They run from `~/.bb/patches` (a LaunchAgent cannot read `~/Documents`);
  `app-patches/install.sh` copies them there and registers the LaunchAgent.
- `handoff/` — fork of Vedran Burojević's Handoff (MIT, keep `LICENSE` and
  the author in the catalog) with Eugene's fixes on top.
- Software Factory (`bisovka-factory`) is deliberately not here yet: it stays
  private in `60-tools/01-workspace-tools/tools/bb-factory/` until Eugene
  decides to publish it.
- `marketplace.json`, `.bb/plugins.json` — generated by
  `scripts/sync-catalog.py` from each plugin's `package.json`. Never edit
  them by hand.

## Releasing anything new

Every new plugin, plugin change, or bb improvement lands here, never in
`60-tools/01-workspace-tools/tools/` or a standalone folder.

1. New plugin: `bb plugin new <id>` in this directory, then rename
   `bb-plugin-<id>/` to `<id>/`. Existing plugin: bump with
   `npm version patch --no-git-tag-version` inside its directory.
2. Store text lives in the plugin: `bb.name`, `bb.description` (one
   sentence), `bb.branding.icon`, optional `PLUGIN_OVERVIEW.md`.
3. `python3 scripts/sync-catalog.py`, then `bb plugin build <id>`.
4. Install the local copy: `bb plugin install ./<id> --yes` (it keeps the
   plugin's settings, secrets, and data), check it live in bb.
5. Commit, then push `main`. Shared installs follow `main`, so a push is the
   release.

A bb.app patch: edit or add the `*.py` in `app-patches/`, then run
`app-patches/install.sh`.

## Rules

- The repository is public (MIT). Nothing personal goes in: no tailnet
  addresses or hostnames, personal URLs, project/thread ids, home paths, or
  private names. Personal values belong in plugin settings or in an
  untracked local file, with a neutral default in code.
- Never change a released plugin id: settings, secrets, data, CLI and
  routes are keyed by it. One plugin can register only one CLI command.
- No secrets or personal data in git: keys go to plugin settings or
  `bb.storage`, never to source. gitleaks runs on commit.
- Each plugin documents its commands and settings in its own `skills/` and
  `README.md`.
- Check that a plugin builds from git alone before pushing: clone into an
  empty directory, `npm install --omit=dev --ignore-scripts`,
  `bb plugin build .` in the plugin.
